Ты — senior AI engineer, backend engineer и product engineer. Твоя задача — не просто описать архитектуру, а СОЗДАТЬ полностью рабочий MVP проекта.

## Задача проекта

Нужно разработать AI-агента, который автоматически отслеживает развитие AI-индустрии через веб-поиск и формирует короткую аналитическую сводку самых важных изменений за последние 48 часов.

Главная задача системы — не просто агрегировать новости, а находить действительно значимые изменения и объяснять:

1. Что произошло.
2. Почему это важно.
3. Что изменилось относительно предыдущего состояния рынка.
4. Какие практические возможности это создаёт.
5. Как событие может повлиять на разработку AI-продуктов.
6. Что конкретно можно попробовать или изменить в продукте/разработке.
7. Если связь естественная — какую потенциальную пользу это может дать крупной технологичной компании уровня Альфа-Банка.

Основная аудитория — product manager / технически грамотный менеджер, которому нужны полезные AI-инсайты, а не поток новостей.

# Ключевой принцип

Система должна оптимизироваться на SIGNAL-TO-NOISE.

Лучше показать 3 действительно важных события, чем 10 посредственных.

Нельзя искусственно заполнять дайджест ради количества.

# Источники

Разрешён только открытый WEB SEARCH.

Не использовать:

* Telegram;
* другие мессенджеры;
* закрытые каналы;
* социальные источники, требующие авторизации.

Можно использовать:

* официальные сайты компаний;
* официальные блоги;
* документацию;
* GitHub;
* arXiv;
* исследовательские лаборатории;
* технологические СМИ;
* независимые технические блоги;
* другие индексируемые веб-источники.

Приоритет источников:

1. Первичный источник.
2. Независимый технический источник.
3. Второй независимый источник.

Для существенных утверждений желательно иметь 2–3 источника.

Заявления самой компании учитывать, но явно отличать:

CONFIRMED FACT

от

COMPANY CLAIM

Например benchmark, опубликованный производителем модели, нельзя автоматически считать независимым доказательством превосходства модели.

Система должна искать как минимум следующие категории.

## 1. Новые AI-модели

Например:

* frontier models;
* open-source models;
* reasoning models;
* multimodal models;
* coding models;
* image/video/audio models;
* специализированные модели.

* снижение latency;
* function/tool calling;
* structured outputs;
* multimodality;
* memory;
* agents.

Не считать важным каждое мелкое обновление.

## 3. Новые архитектурные подходы

Отслеживать только если они потенциально практически значимы.

Не включать paper только потому, что paper вышел.

Research должен попадать в digest, если:

* появился работающий implementation;
* есть заметное улучшение;
* подход начинает использоваться;
* он способен изменить разработку AI-продуктов.

## 4. AI tools

Например:

* agent frameworks;
* coding tools;
* RAG tools;
* evaluation tools;
* orchestration;
* memory;
* MCP и похожие стандарты;
* observability;
* AI infrastructure;
* developer tooling.

## 5. Стоимость AI

Особенно важны:

* изменения стоимости API;
* token pricing;
* caching;
* batch processing;
* новые дешёвые модели;
* способы сократить LLM cost;

GitHub и open-source проекты учитывать только если произошёл практически значимый сдвиг.

# Архитектура AI-системы

Не делать один огромный LLM prompt.

Нужен многошаговый pipeline из отдельных AI-ролей.

Пользователь при этом запускает только ОДНУ команду.

Внутри должна происходить следующая последовательность:

WEB SEARCH
↓
SCOUT
↓
NORMALIZATION / DEDUPLICATION
↓
VERIFIER
↓
CONTEXT ANALYST
↓
IMPACT ANALYST
↓
EDITOR
↓
FINAL DIGEST

Реализовать роли как отдельные prompts/modules.

---

# Agent 1 — SCOUT

Цель Scout — высокий RECALL.

Он должен широко искать потенциально значимые события за последние 48 часов.

Scout не должен слишком агрессивно фильтровать результаты.

Лучше передать дальше несколько лишних событий, чем потерять важное.

Он должен выполнять несколько различных поисковых запросов.

Не ограничиваться запросом вроде:

"AI news today"

Использовать поисковые направления вроде:

* new AI model release
* LLM release
* AI API update
* AI pricing update
* new multimodal model
* new reasoning model
* AI developer tools
* AI agents
* AI open source release
* LLM benchmark
* AI research breakthrough
* AI coding tools
* model context window
* inference cost reduction
* API token price
* AI framework release

Но запросы должны генерироваться динамически.

Scout возвращает структурированный JSON.

Пример:

{
"events": [
{
"id": "...",
"title": "...",
"short_description": "...",
"category": "...",
"published_at": "...",
"sources": [],
"potential_significance": "...",
"entities": []
}
]
}

# Normalization / Deduplication

Одно событие может быть опубликовано десятками сайтов.

Нужно объединять такие результаты в одно EVENT.

Например:

OpenAI выпустила Model X

и

OpenAI launches new Model X

и

Model X announced by OpenAI

должны стать одним событием.

Использовать:

* title similarity;
* semantic similarity;
* entity overlap;
* временную близость.

Для MVP можно использовать embeddings или LLM-based deduplication.

---

# Agent 2 — VERIFIER

Цель — FACTUAL ACCURACY.

Для каждого события необходимо дополнительно выполнить web research.

Проверить:

* действительно ли событие произошло;
* точную дату;
* первичный источник;
* минимум один независимый источник;
* ключевые цифры;
* какие утверждения подтверждены;
* какие являются заявлениями компании;
* какие являются слухами;
* нет ли ошибочной интерпретации.

Verifier должен выдавать структуру:

{
"verified": true,
"primary_source": {},
"independent_sources": [],
"confirmed_facts": [],
"company_claims": [],
"unverified_claims": [],
"key_numbers": [],
"confidence": 0-10
}

Если событие невозможно подтвердить, оно либо удаляется, либо попадает в отдельную категорию UNCONFIRMED.

---

# Слухи

Слухи не запрещены полностью.

Но они НИКОГДА не должны смешиваться с подтверждёнными событиями.

Если потенциально важный слух заслуживает внимания, отображать отдельно:

UNCONFIRMED

Что утверждается.

Почему это потенциально важно.

Откуда появилась информация.

Что подтверждено.

Что НЕ подтверждено.

Confidence.

---

# Agent 3 — CONTEXT ANALYST

Это один из самых важных этапов.

Для каждого подтверждённого события выполнить дополнительный поиск контекста.

Нужно определить:

## Что было раньше?

Например:

Новая модель получила context window 1M.

Нельзя автоматически считать это большим достижением.

Нужно проверить:

* есть ли уже модели с 1M context;
* насколько это новое;
* какие были предыдущие характеристики;
* что предлагают конкуренты.

## Что реально изменилось?

Ответ должен быть RELATIVE, а не абсолютный.

Плохо:

"Компания выпустила модель с контекстом 1M."

Хорошо:

"Контекст 1M уже присутствует у нескольких конкурентов, поэтому сам размер окна не является значимым сдвигом. Более интересное изменение — цена модели на 60% ниже ближайшего аналога."

Контекстный агент должен активно выявлять маркетинговый hype.

---

# Hype detection

Для каждого события определить:

* действительно ли это новое;
* насколько заявление маркетинговое;
* есть ли независимое подтверждение;
* меняет ли событие практическое положение дел.

Допустимые выводы:

LOW HYPE

MODERATE HYPE

HIGH HYPE

Объяснить причину.

---

# Agent 4 — IMPACT ANALYST

Теперь оцени практическую значимость события.

Каждое событие получает пять оценок от 0 до 10.

## Importance

Насколько событие важно для AI-индустрии.

## Novelty

Насколько оно действительно новое относительно существовавшего состояния рынка.

## Practicality

Насколько это можно практически использовать сейчас или в ближайшее время.

## Impact

Насколько событие способно изменить разработку AI-продуктов.

## Confidence

Насколько хорошо подтверждены факты и выводы.

Также рассчитать общий:

SIGNIFICANCE_SCORE

Сделать веса конфигурируемыми.

Базовый вариант:

Importance: 30%
Impact: 25%
Practicality: 20%
Novelty: 15%
Confidence: 10%

Не считать Confidence мерой важности — это мера надёжности информации.

# Анализ практического эффекта

Для каждого события ответить:

## WHAT HAPPENED

Что произошло.

Максимум несколько предложений.

## WHY IT MATTERS

Почему это действительно важно.

## WHAT CHANGED

Что стало иначе относительно предыдущего состояния рынка.

## PRACTICAL OPPORTUNITIES

Что теперь становится возможно:

* дешевле;
* быстрее;
* качественнее;
* проще;
* новый use case;
* новая продуктовая возможность.

## PRODUCT IMPACT

Что это потенциально меняет для команды, создающей AI-продукты.

## WHAT TO TRY

Добавлять только если можно дать конкретную и небанальную рекомендацию.

Например:

"Если команда использует Model Y для document extraction, имеет смысл сравнить её с Model X: при сопоставимом качестве заявленная цена inference ниже примерно в 3 раза."

Не писать банальные рекомендации вроде:

"Следите за развитием технологии."

# Agent 5 — EDITOR

Editor получает только уже проверенные и проанализированные события.

Его задача НЕ заниматься новым research.

Его задача:

* убрать слабые события;
* убрать повторы;
* выбрать действительно важные;
* сделать результат коротким;
* сохранить фактическую точность.

Количество событий динамическое.

Если достойных событий 2 — показать 2.

Если 8 — показать 8.

Никакой фиксированной нормы.

Главный критерий:

"Будет ли технически грамотному product manager полезно узнать это сегодня?"

Если ответ скорее нет — убрать событие.

Не привязывай бизнес-логику проекта намертво к одному search API.

SearchProvider

Чтобы впоследствии можно было подключить разные источники веб-поиска.

Например:

Каждый search result должен содержать хотя бы:

title
url
snippet
published_at

# Очень важное требование: даты

Новости должны реально относиться к анализируемым последним 48 часам.

Не доверять только поисковому snippet.

По возможности проверять дату публикации на самой странице.

Старая статья, которая появилась в search results, не должна считаться новой.

Но старые источники можно использовать для CONTEXT research.

---

# Очень важное требование: причинность

Не делать неподтверждённых выводов.

Разделять:

FACT
CLAIM
INFERENCE

Например:

FACT:
API price снизился с $X до $Y.

INFERENCE:
Это может сделать определённый класс AI-продуктов экономически привлекательнее.

Не выдавать inference за подтверждённый факт.

---

# Очень важное требование: цифры

Если используются:

* цены;
* benchmarks;
* проценты;
* context lengths;
* latency;
* параметры;
* даты;

они должны иметь источник.

Если цифры конфликтуют между источниками — явно указать конфликт.

---

# Дедупликация

Не считать одной новостью:

* релиз;
* benchmark этого релиза;
* изменение pricing,

если это действительно разные существенные события.

Но не создавать 5 карточек из пяти статей об одном релизе.

---

# Тесты

Добавить unit tests минимум для:

* scoring;
* deduplication;
* date filtering;
* event validation;
* source validation.

Добавить fixtures с искусственными событиями.

# Mock mode

Проект должен запускаться даже без API keys.

Добавить:

MOCK_MODE=true

В этом режиме использовать несколько тестовых событий, чтобы можно было проверить весь UI и pipeline.

# Логирование

Для каждого pipeline run сохранять:

* query;
* найденные результаты;
* события после deduplication;
* rejected events;
* причины rejection;
* оценки;
* token usage, если доступно;
* примерную стоимость LLM-запросов, если provider возвращает usage.

---

# Оптимизация стоимости

Не отправлять каждой модели полный текст десятков статей без необходимости.

Использовать staged processing.

Scout работает с небольшими snippets.

Полный research выполнять только для перспективных кандидатов.

После первичной фильтрации более дорогой analysis выполнять только для лучших событий.

---

# Что НЕ надо делать

Не делай:

* сложную микросервисную архитектуру;
* Kubernetes;
* Kafka;
* тяжёлую distributed infrastructure;
* бессмысленный vector DB;
* сложный frontend раньше работающего pipeline;
* autonomous agent loops без ограничений.

Это MVP для соревнования / хакатона.

Главное — качество анализа.

---

# Критерии качества

Система считается успешной, если:

1. Находит действительно важные AI-события последних 48 часов.
2. Не забивает выдачу мелкими релизами.
3. Не дублирует одну новость.
4. Проверяет важные факты по нескольким источникам.
5. Отличает заявление компании от независимого подтверждения.
6. Объясняет не только "что произошло", но и "что изменилось".
7. Сравнивает событие с предыдущим состоянием рынка.
8. Даёт полезные продуктовые выводы.
9. Умеет сказать, что громкая новость на самом деле не особенно важна.
10. Не придумывает факты.
11. Позволяет разобраться, почему событие было выбрано.
12. Не заполняет digest ради количества.

# Порядок твоей работы

НЕ ограничивайся предложением архитектуры.

Сначала:

1. Проанализируй требования.
2. Коротко опиши выбранную архитектуру.
3. Создай структуру проекта.
4. Реализуй data models.
5. Реализуй SearchProvider.
6. Реализуй LLMProvider.
7. Создай prompts для всех пяти AI-ролей.
8. Реализуй pipeline.
9. Реализуй deduplication.
10. Реализуй scoring.
11. Реализуй persistence.
12. Создай Streamlit UI.
13. Добавь mock mode.
14. Добавь tests.
15. Создай .env.example.
16. Создай README с точной инструкцией запуска.

После каждого значимого этапа запускай тесты и исправляй ошибки.

Не оставляй ключевые части в виде TODO или псевдокода.

Если для какого-либо внешнего API требуется ключ, реализуй adapter и configuration, а также mock/fallback, чтобы остальная система была полностью запускаемой.

# Финальный результат

В конце я должен получить репозиторий, который можно запустить примерно так:

pip install -r requirements.txt

cp .env.example .env

streamlit run app.py

и увидеть работающий интерфейс.

Также должна существовать возможность запустить pipeline из CLI:

python -m app.run

Финальный ответ должен содержать:

1. Что реализовано.
2. Структуру проекта.
3. Как запустить.
4. Какие API keys можно подключить.
5. Где находятся prompts.
6. Какие параметры лучше настраивать при сравнении результатов.
7. Какие части проекта являются наиболее важными для дальнейшего улучшения качества.

Главный приоритет проекта:

НЕ количество найденных новостей.

НЕ красивый интерфейс.

А способность максимально качественно определить:

"Какие события последних 48 часов действительно изменили что-либо важное в AI?"
